# westy_scan 性能基准（M1）

> 数据来源：本机实测，命令可复现（见文末）。**真实网络的吞吐取决于 RTT、丢包与限速配置**，
> 文中的推算模型比数字本身更重要。

## 1. 测试环境

| 项 | 值 |
| --- | --- |
| CPU | AMD Ryzen 7 7735H（16 逻辑核） |
| OS | Windows 11 / Go 1.27.1 windows/amd64 |
| Go 工具链 | 便携版，`.tools/go`（`GOPROXY=off` 零依赖构建） |
| 拓扑 | 全部为 loopback（127.0.0.1），无网络抖动 |

## 2. 微基准（实测）

```bash
.tools/go/bin/go.exe test ./internal/portscan/... -run XXX -bench . -benchtime 3x
```

| 基准 | 结果 | 说明 |
| --- | --- | --- |
| `BenchmarkConnectScanLocalhost1000` | **31.1 ms/op → 31,368 ports/s** | 1000 个端口、并发 200、全部关闭（RST）、不抓 Banner；1.9 MB/op、28,692 allocs/op |
| `BenchmarkBuildSYNPacket` | 280 ns/op | 构造 IPv4+TCP SYN（含两个校验和），48 B/op |
| `BenchmarkParseIPv4TCP` | 240 ns/op | 解析原始回包，96 B/op |
| `BenchmarkScopeGuard` | 440 ns/op | 授权闸门（含 DNS 缓存命中路径） |

**读法**：31,368 ports/s 是"扫描引擎 + 本机 TCP 栈"的上限，**不是**真实网络的吞吐。
它说明引擎自身没有成为瓶颈（每端口约 32 µs 的调度开销），真实场景一定受网络支配。

服务识别（probe）自身的 CPU 开销可忽略（都是几十字节的解析），真正的成本是**网络往返**。

## 3. 服务识别的时间成本

| 场景 | 额外开销 |
| --- | --- |
| 端口已知且有专用探针（22/3306/6379/445/3389/27017…） | +1 次 RTT（一次握手往返） |
| 端口是 Web 端口 | 0（走 HTTP 探测路径，证书信息顺带拿到） |
| 未知端口 | 先试 HTTP（Web 路径），失败后再试 TLS，最长多等 1.5 s（TLS 探测对非 TLS 服务的收敛超时） |
| 有 Banner 且是文本协议（SSH/FTP/SMTP/VNC） | 0（直接复用端口扫描阶段的 Banner，不再发第二个包） |

实测（`scripts/demo-m1.ps1`，6 个本地假服务 + 1 个 UDP DNS 应答器）：**7/7 全部识别成功**
（OpenSSH 9.6p1 / MySQL 8.0.35 / PostgreSQL / Redis 7.2.4 / Memcached 1.6.17 / VNC 3.8 / DNS），
整轮耗时约 3 秒（其中 PostgreSQL 等探针各占一个 RTT，loopback 上主要是调度开销）。

## 4. 真实网络的吞吐推算模型

单机扫描的总耗时近似为：

```
总耗时 ≈ 探测数 / min(并发数 / RTT, 限速值)
```

其中 探测数 = 主机数 × 端口数。举例（1000 端口 × 256 台 = 256,000 次探测）：

| 场景 | RTT | 并发 | 限速 | 预计耗时 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 同网段千兆内网 | 0.3 ms | 200 | 不限 | ≈ 0.4 s（理论） | 实际受交换机/防火墙会话表限制，通常 5–20 s |
| 跨网段内网 | 1 ms | 200 | 不限 | ≈ 1.3 s（理论） | 同上 |
| 跨网段内网（推荐配置） | 1 ms | 200 | 1000 pps | ≈ 256 s | **限速成为主导项**，这也是默认建议 |
| 全端口扫描 /24（65,536 × 256） | 1 ms | 200 | 不限 | ≈ 84 s（理论） | 现实中必须限速，否则会触发 IDS |
| SYN 扫描（Linux，需 root） | 1 ms | 200 | 不限 | 与 connect 同阶 | 优势在"不开完整连接"，不是在这张表里 |

**结论**：并发调大对真实网络的收益远小于预期，**限速几乎总是主导因素**。
默认 `-rate 0`（不限速）适合本机/实验网，生产网段请从 `-rate 500~1000` 起步。

## 5. 容量与文件描述符

- connect 扫描每个在途连接占 1 个 fd，峰值 ≈ `concurrency`；
- 框架启动时会检查 `RLIMIT_NOFILE`（Linux/macOS），低于 `concurrency × 2 + 64` 会打印告警；
- Linux 建议：`ulimit -n 65535`（或 `LimitNOFILE=65535`）。

## 6. 基准之外的已知成本

| 项 | 影响 |
| --- | --- |
| Banner 抓取 | 每个开放端口多 1 次读（最长 `-timeout` 秒），关闭用 `-banner=false` |
| Web 探测 | 每个 Web 端口最多 2 次请求（http 失败再试 https） |
| 爬虫 | 按页数上限，默认 500 页、深度 2、10 并发 |
| SYN 扫描 | 需要收包协程常驻，吞吐受"发包速率 + 收包解析"两端影响；本机未见瓶颈 |

## 7. 与同类工具的定位对照（**不是**性能对比）

先把话说清楚：**我没有做同机横向性能测试。** 原因很实际——本项目要求离线可构建，
环境里没有、也无法安装 nmap/masscan/fscan，而且它们与本项目的目标不同：
masscan/nmap 是 C 实现的老牌工具，fscan 是 Go 项目，**不同软件在不同机器上跑出来的数字没有可比性**。
下表是**能力边界与定位**的对照，性能一栏只写各工具官方/公开的说法，并明确标注来源性质。

| 工具 | 核心定位 | 端口扫描方式 | 应用层能力 | 性能口径 | 与本项目的关系 |
| --- | --- | --- | --- | --- | --- |
| **masscan** | 互联网级端口发现 | 无状态 SYN（自建 TCP 栈） | 几乎没有（不做应用层识别） | 官方宣称可到千万级包/秒（**官方数字，非我实测**） | 端口发现速度的标杆；本项目**不与之竞争速度** |
| **nmap** | 服务/版本识别 + NSE 脚本 | connect/SYN + 丰富的探测探针 | 很强（NSE 生态） | 单机全端口通常是分钟级（**公开常识，非我实测**） | 服务识别深度上仍需向它学习 |
| **fscan** | 内网综合扫描 + 常见漏洞利用 | connect（Go 并发） | 内置一套利用/弱口令模块 | 未公开统一口径 | 定位最接近；差异见下 |
| **nuclei** | 模板化漏洞验证 | 不做端口发现 | 极强（模板生态数千条） | 取决于模板数与目标数 | 本项目模板引擎的思路参考；弹药量级差距明显 |
| **westy_scan（本项目）** | **授权场景的资产测绘 + 只读验证 + 变更对比 + 合规闭环** | connect（全平台）/ SYN（仅 Linux） | 12 类协议握手 + 256 条指纹 + 130 条只读模板 | 本机 connect 扫描 **31,368 ports/s**（1000 端口、并发 200，可复现） | 定位差异在"合规与工作流"，不在"谁快" |

### 本项目的差异化在哪（这才是该讲的部分）

1. **合规闭环**：单点合规出口（allow/deny/CIDR/域名 + **DNS 解析后复检**）+ 授权书绑定 + 全量审计；
   分布式下授权判定**下沉到 Agent**（两层闸门）。同类工具大多假设"你已经在合法环境里"。
2. **变更对比的数据模型**：每次扫描记录"观察集合"，能正确回答"这轮比上轮多了什么、修好没有"，
   而不是把重复扫到的漏洞误报成"已修复"（这个 bug 我在 M6 真踩过）。
3. **可验证的质量门禁**：规则库三道门禁（编译校验 / 空匹配检测 / 金丝雀契约），
   把"模板是不是死的"变成构建期事实。
4. **零依赖单二进制**：隔离网直接落地，不需要运行时与依赖树。

### 本项目明显不如它们的地方（不要吹）

- **速度**：masscan 的无状态 SYN 是数量级优势；本项目的 connect 扫描受 fd 与调度限制。
- **服务识别深度**：nmap 的探针库与 NSE 生态远超 12 类握手。
- **漏洞覆盖**：nuclei 数千模板 vs 本项目 130 条只读模板；fscan 的弱口令/利用模块本项目完全没有。
- **真实环境验证**：这三者都有大量真实使用反馈，本项目**一次真实网络都没打过**。

> 结论：如果任务是"扫一个 B 段看哪些端口开着"，用 masscan；
> 如果是"给客户做一次有交付物、有合规留痕、要回答'这次比上次多了什么'的授权评估"，
> 本项目的形态才是对的方向。**讲清定位比讲数字更有说服力。**

## 8. 复现方法

```bash
# 微基准
.tools/go/bin/go.exe test ./internal/portscan/... -run XXX -bench . -benchtime 5x -benchmem

# 服务识别端到端（本地假服务，不接触任何第三方目标）
powershell -ExecutionPolicy Bypass -File scripts/demo-m1.ps1

# 本地闭环（端口 + HTTP + 爬虫）
powershell -ExecutionPolicy Bypass -File scripts/demo-local.ps1
```

> 提醒：任何真实网络基准都必须在**书面授权**的范围内进行，并提前与目标方约定测试窗口与限速上限。
